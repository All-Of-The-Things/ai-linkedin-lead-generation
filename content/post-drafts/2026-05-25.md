## Post A — Migrating from SuiteCommerce to Shopify without assigning a single source

Migrating from SuiteCommerce to Shopify without assigning a single source of truth for data ownership is a direct path to rework.

The basics have to be covered: prices from NetSuite must stay consistent in Shopify as per the customer's agreement, Shopify shouldn't onboard customers already in NetSuite, inventory updates should flow in a way that prevents oversells.

Projects kick-off integrations under the assumption that there's agreeement as to how this should work, without anything in written.

A basic sequence that should be standard: data ownership map in Discovery, field-level mapping before implementation kick-off, validation checkpoints before cutover to confirm every flow works both ways as per requirements.

Data ownership brings the clarity needed before kick-off to guarantee build once and grow from there.

## Post B — SuiteCommerce to Shopify migrations running over budget were missing at lea

SuiteCommerce to Shopify migrations running over budget were missing at least one of these artifacts before build started.

At AOTT we have a set of resources we develop as part of Discovery to prevents assumptions and help mitigate risks caused by lack of definition.

Each artifact below is a category of mid-build disruption, not a pre-launch checklist item.

1. **Integration ownership matrix:** which system is source of truth per data type (pricing, customer, inventory)
2. **Field-level data mapping:** NetSuite record types mapped to exact Shopify objects, before build starts
3. **B2B pricing rule inventory:** account-level rules, volume tiers, contract rates
4. **App stack audit:** what Shopify replaces natively vs. what requires custom development
5. **Error handling spec:** failure states per integration, alerting, retry behavior
6. **Cutover sequence:** validation checkpoints per integration, not a single go/no-go
7. **Rollback criteria:** the exact conditions under which go-live is paused

Each of this represent a question that wasn't answered in Discovery.

Don't let that miss become expensive rework later by ensuring these are covered before build starts.

## Post C — Celigo being live means your happy path works. A production-ready integrati

Celigo being live means your happy path works. A production-ready integration means there's an exception handling layer ready for unexpected scenarios.

A connector handles the happy path: record created in NetSuite, syncs to the destination.

What it doesn't handle by default is the layer that keeps it running at 2am. Token refresh when credentials expire. Error categorization per record type so a single bad record doesn't halt the queue. Alerting when a sync failure goes undetected for hours. Retry logic that distinguishes a transient timeout from a permanent data rejection.

For a B2B distributor with real-time inventory in NetSuite, a sync failure at 2am that goes undetected until morning means oversold orders, incorrect fulfillment confirmations, and customer-facing pricing that no longer matches the ERP.

## Post D — A B2B quote request submitted through SuiteCommerce is not the same as a B

A B2B quote request submitted through SuiteCommerce is not the same as a B2B quote that's accurate.

SuiteCommerce handles the front end natively: quote submission, estimates surfaced back to the portal. No custom configuration needed for the submission itself.

Pricing, availability, and estimate status all come from NetSuite. The portal renders what NetSuite returns. If NetSuite isn't configured correctly, the portal has nothing accurate to show.

This is where the gaps surface: list price instead of the customer's negotiated tier, estimates missing fulfillment constraints, no approval trail on custom pricing.

Portal live means the front end works. Quotes that convert means NetSuite is configured to back them. All Of The Things scopes NetSuite setup as part of every B2B portal project.

## Post E — Shopify Functions is not a customization layer. It's a replacement for busi

Shopify Functions is not a customization layer. It's a replacement for business logic you were running somewhere else.

Functions handles discount rules, cart transforms, payment method gating, and delivery customizations. It runs on Shopify's infrastructure, not as an app you install and configure on top.

The mistake is running the same rule in two places. A volume discount synced from NetSuite via connector and a Functions extension applying the same logic on checkout. Both execute. The cart behavior becomes unpredictable.

Keep business logic in a single place: leverage the connector for what flows between systems, rely on Functions for eCommerce-only behavior.

## Post F — Migration scope isn't a list of what needs to move. It's a classification of

Migration scope isn't a list of what needs to move. It's a classification of how each item gets there.

Every item falls into one of three buckets: automate, manual decision, or custom dev. Automate means the data moves via connector with no human input required. Manual decision means a business rule needs to be confirmed before field mapping is built. Custom dev means the behavior doesn't exist natively in Shopify.

The manual decision bucket is where timelines slip. Undocumented SuiteCommerce behavior, data inconsistencies, rules that need sign-off from someone unavailable during the build. A developer who hits an undecided item mid-sprint guesses, skips, or blocks.

Appropriate classification ensures on-time delivery: the work ahead is predictable, and scope stays locked to what you learned in Discovery.

## Post G — Claude Code won't get you a market-ready product from a vague brief. Claude

Claude Code won't get you a market-ready product from a vague brief. Claude Code needs a structured, iterative approach that keeps the Spec as the main asset for guidance to develop something valuable.

The pipeline starts before any code is written. A structured `idea.json` goes in. Claude generates a proposal, then produces the spec files: `core.md` defining what the system does and doesn't do, `architecture.md`, `logic.md`, `data-model.json`, and a platform spec for Shopify or NetSuite projects. Claude Code executes against those files, not against a prompt.

A second layer prevents rework: locked skills. Authoritative reference files for NetSuite SDF permission IDs, SuiteQL rules, and Shopify API mutations that Claude must search before writing code. Wrong API calls and hallucinated permission IDs get caught at the Spec layer, before they reach the build.

The developer's role shifts to writing precise input and validating output against the spec. Rework is a Spec problem, not a code problem.
